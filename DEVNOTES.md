### Last chapter closed: Chapter 4 (chase regression on domt2_1, commit `3e3fcfa9`)

The ACTUAL fix was the chase-drive gateway pass-through in v0.17.8.19.4. The previous three builds (.19.1, .19.2, .19.3) chased a wrong diagnosis (prune over-trimming the chase path); they're kept as defensive infrastructure that produces a denser, more robust chase path that the pass-through then steers through cleanly.

**Root cause.** In `UpdateAutoDrive` (`src/field_nav_autodrive.inl`), the v0.15.9.2.15 'offset 300 units past line' logic correctly mutates `tx, tz, dx, dz` to push the target through the gateway. But the waypoint chain-advance block LATER in the same function overwrites `dx, dz` with `steerX/steerY = s_waypoints[last]`, which is the gateway CENTER. The offset is silently discarded. Party aims AT the gateway, not THROUGH it. Engine wall-sliding produces UR-direction wobble at the corner of the goal triangle. Battleyarou (TALKRAD ~500) catches the wobbling party.

**Fix shape.** ~25-line block in `field_nav_autodrive.inl` inserted directly after the waypoint chain-advance sets `vecWpRawX/Y`. Gated on `s_chaseDriveActive && s_driveCrossLineActive && s_waypointIdx == s_waypointCount - 1`. Computes player→gateway unit vector, sets `steerX/steerY` to a point 300 units PAST the gateway center along that direction. Arrival is still owned by the cross-product sign-flip check in the `gotCrossLine` block above.

**BAT signals (2026-05-28 19:39).** `[funnel-prune] skipped for chase-drive (32 waypoints kept)`, `[drive] chase-drive gateway pass-through: ... toGwLen=457 → 428 → 398 → ...`, zero `[CBF] PASS chase BATTLE` lines, MAPJUMP to Lapin Beach fired cleanly.

**Lessons (carry-forward).**
1. When a fix doesn't engage as expected, READ THE LOG before iterating. v0.17.8.19.2's new 'skipped for chase-drive' log line didn't fire in the BAT — that should have been the first clue (caught only in v0.17.8.19.3).
2. When 'fix' after 'fix' leaves the BAT outcome IDENTICAL (three consecutive identical-coordinate catches at (-110,-3407)), the original diagnosis is probably wrong.
3. Chase-drive's chain-advance NEVER advances past the last waypoint. The funnel's last waypoint sits at the gateway center. Without an explicit override, `steerX/steerY` aims AT the gateway, not THROUGH it.
4. The v0.15.9.2.15 'offset 300 units past line' logic IS NOT ENOUGH on its own. It mutates `tx, tz, dx, dz` but those values are overwritten by the waypoint chain-advance later in the same function. The resolver produces a correct VARBLOCK marker (`0x800000xx`), but PSHM-DEST finds no init-method writer for that variable ("0 found writers") and uses the variable's ADDRESS as the field id instead of its VALUE. The address only coincidentally resembles a real field id.
- The 'gateway switches' symptom lives one field upstream on corridor **bgroad_5**: pre-SeeD its exit resolves `addr=0x00ED -> field 237 (Dormitory Double 1)` — correct by coincidence (0xED==237). Post-SeeD the game routes that gateway to the single room, but addr-as-literal would still say 237, blind to the varblock value. That is the exact 'label won't switch' symptom.
- Second facet: in the single room, the actual door is a Map Exit entity 'l1' that the mod DROPS (`MAP_EXIT 'l1' dropped: no position, unresolved dest (param=-2147483648)`) — so post-SeeD the real exit is missing from the catalog, not just mislabeled.
- **Proposed fix — SUPERSEDED (v0.17.9.2): the live varblock read is DEAD.** The walk-through MAPJUMP-hook BAT showed that at fire time `varblock[0xAE]=0` while the engine's destField was 228 — the destination is NOT stored in the varblock at the marker address at any lifecycle point. It is a hardcoded **immediate operand of whichever MAPJUMP3 the script branches to** (bgryo2_1 'squalls' carries ->228 Hallway 5, ->231, ->174 Hall 10), chosen by flag-gated control flow. The resolver's marker `0x800000AE` is itself an artifact of mis-decoding an immediate push (operand 0xAE) as a varblock address (it ignores the push bank field; bank 0 = immediate). **Correct fix = a forward concrete JSM micro-interpreter** at catalog-build time: follow JMP/JPF/JMPB using live variable reads for the branch conditions, model pushes/compares, stop at the first reached MAPJUMP3, read the bank-decoded destField off the virtual stack. Read-only, never calls the engine MAPJUMP3 / never writes 0x01CE4762; no caching, no manual traversal, tracks story state automatically. **v0.17.9.2** ships the LOCAL `[BC-DUMP]` disassembler (in `field_archive_jsm_mapjump_resolver.inl`, gated to bgryo2_1/bgroad_5/bghall_5) to expose the branch structure before writing the interpreter. Acceptance test: interpreter resolves bgryo2_1 -> 228 against current memory.
- **Ground truth (Aaron, 2026-05-29) — confirms live-read is the ONLY correct approach:** both dorm rooms currently exit to the dorm corridor (Hallway 5); addr-as-literal mislabels them "Hallway 8" (231, bgryo1_1) and "Hall 10" (174, bgryo2_1). The single room's (bgryo2_1) exit destination ALSO changes with STORY PROGRESSION via the same varblock 0xAE: Hallway 5 at this point in the game, then later skips the hallway and goes directly to B-Garden Hall 10 (174). So "Hall 10" is wrong NOW (should be Hallway 5) and only coincidentally right late-game (0xAE==174). Same field, same exit, two different correct destinations depending on story flags — there is NO static answer and no single writer. This rules out static-resolution refinement AND (per the v0.17.9.2 finding above) a varblock read at the marker address; the destination is an immediate operand selected at runtime by flag-gated branches, so only executing the branch logic (the JSM interpreter) reproduces it.
